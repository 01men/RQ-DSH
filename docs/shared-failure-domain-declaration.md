# 共享故障域声明（审批执行链）—— OPT-P2-02

> 依据《榕器 ybkk-AIOS 优化执行方案》P2-02：高危审批采用"独立最小化规则源"降级设计，
> 不宣称密码学级"独立保护"。本文档是该取舍的显式声明与残余风险登记。

## 1. 范围

审批主链路：`createApproval`（开单）→ `decideApproval`（决策/执行）→ `registerExecutor`（执行器）→ `registerCompensation`（补偿）。

## 2. 已实现的隔离层（进程内强度）

| 隔离层 | 机制 | 强度口径 |
|---|---|---|
| 执行能力令牌 | `approvalCapabilityVault`（模块闭包）：随机 token + 一次性 + 绑定 action/主体 + 30s TTL | 进程内不可伪造（非密码学承诺；模块边界隔离） |
| 独立规则源 | `approvalKindRule()` 静态规则表（二次确认/敏感面策略） | 可评审、可 diff 的静态工件；与主授权判定（`authorizeAgainst`）代码路径分离 |
| 敏感面卫生 | `scanSensitiveKeys`/`maskSensitivePayload`：reject 类 kind 拒绝开单；mask 类掩码入库 + `maskedKeys` 留痕 | 敏感值零进审批存储（红线一的同源延伸） |
| 失败补偿 | `registerCompensation` 注册表：executor 失败 → 编排补偿 → 回写审批单 + `approval.compensated` 审计 | 补偿失败显式标记"需人工介入" |

## 3. 共享故障域（未隔离项，诚实登记）

1. **同进程**：开单/决策/执行器/补偿运行于同一 Node 进程，共享 GC、事件循环与文件系统；
   宿主进程被攻陷即全部沦陷（威胁模型明确不含宿主级攻击，见方案第五章取舍）。
2. **同权限**：执行器以平台服务身份运行，无独立最小权限操作系统账户。
3. **同代码**：规则表与执行器同仓库同发版——规则表的"独立性"是**评审独立性**（可 diff、可否决），
   不是部署独立性。上游仓库投毒可同时篡改两者。
4. **总线依赖**：审批事件经 `platformBus` 广播；总线降级（OPT-P1-04 死信/重试）不伪造事件，
   但审批审计的实时性依赖总线健康。

## 4. 升级路径

- 若产品要求真正的独立保护（独立进程/独立硬件/密码学域），须立项独立审批执行器服务
  （方案第五章：本版本明确不投入）。
- 仓库启用提交签署（`requireSignedCommits=true`，OPT-P2-03 开关）后，
  update_apply 的签名核验从"记录口径"升级为"强制闸门"。
