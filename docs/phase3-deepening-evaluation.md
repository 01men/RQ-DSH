## WP-14 ROI 看板对接用工成本模型——已落地（随 WP-12 看板 v1 下发）

- **落点**：`/api/portal/board` 响应新增 `roi` 区块（portal 只读聚合，不开特权接口）。
- **口径**：替代工时 = 调用次数 × 单次替代分钟（`ROI_MINUTES_PER_CALL`，默认 3）÷ 60；人力成本 = 替代工时 × 综合人力时薪（`ROI_LABOR_COST_CENTS_PER_HOUR`，默认 5000 分=50 元）；ROI 对比基准 = usage 周聚合平台成本（WAIC.chargeCents）。
- **调用基数**：优先取 mcp ok 调用数（completed），无完成数据时回落 usage 事件数——口径声明（`roi.note`）随响应下发，看板侧必须以「估算」字样呈现，防止误读为实测值。
- **自测**：selftest「战略看板与目录瘦身」节断言 roi 三系数与口径声明在册。

## WP-15 app 编排可视化画布例外条款评审——评估完成，默认不另起栈

**结论**：维持 V2.0 §2.3 默认决议（不引入第二前端栈、不做画布），给出如下**例外触发条件**（满足任一即重新立项评审）：

1. 出现 ≥3 个在产 app 的编排逻辑超过 5 步串行/含条件分支，纯表单配置错误率显著上升（以 app 发布回滚次数/月 > 2 为代理指标）；
2. 客户明确以「可视化编排」为采购硬条件（销售侧书面需求 ≥2 家）；
3. KBaaS 上线后知识包编排（检索→生成→审核）成为主流场景，数据流画布需求自然涌现。

**若触发的推荐路线**（评审预置，避免临时选型）：复用 dsh 客户端插件机制（`conversation.view` 视图 Tab 槽，见 `docs/spike-dsh-client-capability.md` §3.2）承载画布视图；数据面走既有 app schema 与 `POST /api/apps` 契约，画布仅是同一 JSON 的图形化编辑器——零后端新增，前端栈收敛在 dsh 客户端 React 体系内。

## WP-16 管理动作 Agent 化扩展评估——评估完成，路线已预置

**现状盘点**：平台插件经 `src/tools.ts` 注册的 dsh 原生 ToolRuntime 工具已达 64+（文档口径 37 为部署文档写作时点），宿主一体化形态下对模型可见可调——「管理动作自然语言完成」已由 dsh-ops-admin 系列 skill 覆盖（iam/authn/mcp/skillhub/agent/app/audit 七域）。

**审批动作卡片化（会话内审批）可行性**：

| 要素 | 结论 |
|---|---|
| 技术通道 | rq-card 注入插件已验证会话卡全链（slot 注册 + 工具生命周期订阅 + 同源 REST 回流，WP-06）；审批卡片 = 新增 `approval.request` 生命周期监听 + `conversation.chat.assistant-actions` 式动作条 |
| 合规约束 | 高风险审批的**二次确认必须在控制台完成**（WP-10 服务端强制 confirmed）：会话卡可呈现「待审批」摘要 + 跳转深链（`#/approvals?focus=<id>`），但**不建议**在会话内直接 decide——会话面缺少审批人强身份核验（rq_sid 绑定 ≠ 审批权限核验），且二次确认交互在聊天流中易被误触 |
| 建议路线 | ① 一期：approval.created 事件 → 会话通知卡（只读 + 深链跳转），零权限风险；② 二期（需 authority:'loopback' 之外新增审批人身份核验 RPC 后）：低风险（medium 及以下）审批会话内 decide + 高风险仍回控制台 |

**触发条件**：审批中心日待办 > 20 单且审批人活跃于宿主会话（behavior 会话侧埋点可观测）时启动一期。
