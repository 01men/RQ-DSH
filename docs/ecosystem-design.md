## 〇、全景：平台该提供的十项服务

从超级个体（1–3 人团队）的完整旅程看，平台可提供的服务共十项，分四层：

```
┌─────────────────────────────────────────────────────────────┐
│ 分发运营层  ⑦ 插件市场与渠道分发   ⑧ 开发者门户与支持体系      │
├─────────────────────────────────────────────────────────────┤
│ 商业层     ⑤ 模型网关与算力转售   ⑥ 计量计费与分成结算        │
├─────────────────────────────────────────────────────────────┤
│ 企业能力层  ② 身份认证赋能(auth)   ③ 数据与知识基础设施       │
│            ④ Agent 运行时组件                                 │
├─────────────────────────────────────────────────────────────┤
│ 工程底座层  ① 插件契约与沙箱      ⑨ 可观测性与托管运维        │
│            ⑩ 安全合规与治理                                    │
└─────────────────────────────────────────────────────────────┘
```

配套的三条支撑路径（对超级个体的接入分层）：

| 路径 | 接入方式 | 个体改造成本 | 平台收益 | 阶段 |
|---|---|---|---|---|
| A 轻接入 | 仅接模型网关 API + OIDC 登录（不做插件化） | 低 | API 差价 + 认证订阅费 | 先行 |
| B 插件化 | 按 dsh 第三方插件契约改造，上架市场 | 中 | 抽佣 + 生态绑定 | 中期 |
| C 共建孵化 | 联合品牌、交付资源、投资/收购头部场景 | — | 供给独占 | 远期 |

商业飞轮：**平台把企业级脏活（认证/权限/审计/知识库/连接器/合规/运维）做成公共服务，
让个体只专注场景逻辑；个体的插件又丰富了平台对企业的吸引力——供给与需求互相拉动。**
接入门槛（契约 SDK + 脚手架 + 一天内 Hello World）决定生态成败。

### 〇.1 外部插件复用结论（本版明确）

DSH 官方文档站目前**没有插件市场、生态清单或推荐插件页**（quickstart 仅覆盖
Web UI 使用，develop 章节仅覆盖从零开发）。因此：

- 本方案所有平台能力（billing、KBaaS、连接器市场、托管运维……）均以**自建
  dsh 插件**落地，不依赖、不等待外部现成插件——这是当前唯一正确选择；
- 唯一记录在案的外部复用项是 OS-skill 的钉钉机器人渠道（roadmap 已记触发条件
  与实施手册），届时以 `dsh-plugin-channel-dingtalk` 新插件落地，向 app 插件
  注册渠道扩展点；
- 若官方未来发布插件市场/生态规范，再评估对接，不影响本方案任何排期。

## 一、插件契约与沙箱（服务 ①，工程底座）

### 1.1 设计原则

内部插件享受全部信任；第三方插件只通过「声明 + 审批 + 沙箱」获得最小必要能力。
契约的本质是把插件协作铁律（事件总线、禁止直连数据）从“自觉遵守”变成“强制不可违反”。

### 1.2 两层契约：官方加载契约 + 平台治理层（本版重点澄清）

**分层原则**：第三方插件的**技术加载层完全遵循 DSH 官方插件规范**——
插件即导出 `apply(ctx)` 的 TypeScript 模块，经 `inject` 声明服务依赖（框架保证
依赖就绪后才运行），通过 `ctx` 注册能力、`ctx.effect()` 管理手动清理，事件监听/
工具/定时器随插件卸载自动清理。加载机制与现有 11 个平台插件完全一致
（cordis.yml `insert + config`）。**manifest 五件套是加载层之上的平台治理层**
（身份/权限/提供面/事件/计费声明），不替代、不绕开框架契约——第三方开发者
写的仍是标准 cordis 插件，只是额外提交治理声明并在平台侧接受校验。

治理层五面：

```
third-party-plugin/
  plugin.yaml          # ① 身份与依赖
  manifest/
    permissions.yaml   # ② 权限声明
    apis.yaml          # ③ 提供面（REST + 工具）
    events.yaml        # ④ 事件契约
    billing.yaml       # ⑤ 计费声明（见第四节）
  src/index.ts         # 标准 cordis 插件入口：export apply(ctx)
```

**① 身份面（plugin.yaml 扩展）**

```yaml
id: com.superview.contract-review
version: 1.2.0
publisher: dev_superview          # iam 中的开发者账号
signature: <包内容签名>            # 上架时以发布者公钥验签
depends:
  - dsh-plugin-platform-core: ^1.0
capabilities_request:             # 平台能力白名单申请，逐条审批
  - model-gateway.invoke
  - knowledgebase.read
  - audit.emit
sandbox:
  network: allowlist              # 出网白名单
  storage: plugin-scoped          # 只能访问 plugin:<id>: 前缀集合
```

- 第三方插件**没有自有数据库**：存储由 platform-core 按命名空间前缀强制隔离，
  复用 `collection.uniqueOn()` 引擎，仅加前缀校验。
- **沙箱执行分级**（按风险递增）：
  - L0 纯声明式（只有 manifest + 提示词/配置，无代码）——最快上架，最先支持
  - L1 托管 JS 沙箱（代码在受限运行时执行，禁 require/fs/net 白名单外访问）
    ——**自研件，工作量不小，须按独立里程碑评估**：cordis 插件与宿主同 Node
    进程运行，框架只有服务级隔离（inject 声明），没有进程/模块级沙箱语义；
    需自定义模块加载路径（`vm.SourceTextModule` 或 worker 隔离）重写加载器，
    并解决 ctx 代理、能力裁剪、超时与资源配额。**不与 L0/市场上线捆绑排期**，
    在 L0 验证跑通后再立项
  - L2 容器级隔离（独立进程/容器，网络经平台代理）——重场景后置

**② 权限面**：权限点注册进统一 RBAC，但带 `requested → approved` 审批态；
安装到具体企业时可被该企业管理员**再收缩**（只开一半权限也可用）。

**③ 提供面**：路由注册自动获得前缀 `/api/plugins/<id>/`、网关鉴权、调用计量三件套；
工具暴露走 dsh ToolRuntime 契约——第三方工具天然可被平台上的 Agent 调用，
**这就是“他的应用变成平台能力”的分发机制**。

**④ 事件面**：订阅仅限平台显式广播的公共事件；发布强制 `source: plugin:<id>`
命名空间，bus 层校验，无法伪造平台事件。
（cordis 事件系统本身没有 source 校验钩子——该校验在 platform-core 的
platformBus 封装层实现，属平台自研能力而非框架能力，实现时须覆盖直发
`ctx.emit` 的旁路。）

**⑤ 计费面**：见第四节。

### 1.3 生命周期与上架

第三方插件注册为 resource-core 的一种资源类型，走状态机：

```
submitted → scanning → approved → listed →
(per-org) install_requested → org_approved → running →
suspended / deprecated / offlined
```

上架流程推广 skillhub 已验证模式（提交 → 静态扫描 → 两级审批 → 版本化上架），
扫描新增：声明与行为比对（申请 `knowledgebase.read` 却摸其他集合）、
出网白名单外调用、事件命名空间合规。

**版本兼容**：`depends` semver；公共事件 schema 变更走 deprecation 期
（发 `platform.schema.deprecated`，插件自适配）——与 `skill.deprecated → Agent 告警` 同机制。

### 1.4 开发者体验（成败关键）

- `dshctl plugin init` 脚手架：生成契约骨架 + 可运行 demo
- `dsh-plugin-devkit`：platform-core 的 mock（内存事件总线 + 假 IAM），离线开发
- 目标：从 init 到本地跑通 ≤ 30 分钟
- 契约自验证（**硬性验收标准**）：**用 app 插件按第三方契约重写跑通**——
  app 的编排拓扑是全部业务插件中最复杂的，是最好的试金石，能暴露所有
  “想不过”之处；这是最便宜的契约验证方式，第 3 步未通过则契约不冻结

## 二、身份认证赋能 / auth-identity 对外化（服务 ②）

authn 从“平台内部登录能力”升级为对外的 **Identity Provider**，按接入深度三档：

### 2.1 模式 A：托管身份注入（市场插件，深度最大）

- 插件零登录代码：用户经平台控制台进入插件 UI，网关注入 on-behalf-of 令牌
  （用户身份 → 插件机器身份链）
- 插件后台任务用机器凭证（推广 agent 插件已有机制）
- **唯一改造点**：令牌签发支持 audience/scope——scope 写明 `plugin:<id>`，
  令牌泄漏也不能拿去调别的平台能力
- 身份、权限、计量在网关一次解决

### 2.2 模式 B：平台作为 OAuth2/OIDC IdP（外部独立应用）

适用不做插件化改造的独立应用——与路径 A 配套，把登录和企业身份“外包”给平台：

```
第三方应用 → 302 → platform /oauth/authorize（平台登录页/扫码）
          ← code → 后端换 token → /userinfo → NormalizedProfile（含 org、角色）
```

- 第三方应用零登录代码获得企业 SSO、组织架构、一人一号约束
- **杀手级卖点**：用户在平台被冻结/离职 → `iam.user.frozen` → authn 吊销令牌 →
  第三方应用下个请求即失效。这种企业级联防是个体自建登录永远做不到的
- 命中 roadmap 暂缓项 **RS256/ES256 + JWKS 轮换**（IdP 对外签发，HMAC 不再够用），
  升级路径已记录：authn 插件内换库 + 暴开 `/.well-known/jwks.json`

### 2.3 模式 C：身份联邦（企业客户自有 IdP）

平台作为 Relying Party 对接企业 AD/钉钉/飞书。v1.1 的 `IdentityProviderAdapter`
统一抽象正为此准备：每接一家企业 IdP 只加一个 Adapter 实现，主流程零改动。
对个体的价值：他的应用经由平台天然支持任何企业客户的自有登录，无需逐家适配。

### 2.4 三模式对照

| | A 托管注入 | B 平台作 IdP | C 身份联邦 |
|---|---|---|---|
| 适用对象 | 市场插件 | 独立外部应用 | 企业客户自有 IdP |
| 个体改造成本 | 高（插件化） | 低（接 OIDC） | 零 |
| 平台控制力 | 最强 | 中 | 中 |
| 商业模式 | 抽佣 + 分成 | 认证订阅费 | 平台竞争力项 |
| 依赖改造 | token scope/aud | RS256 + JWKS | Adapter（已就绪） |

## 三、数据与知识基础设施（服务 ③）+ Agent 运行时（服务 ④）

超级个体最耗时的重复劳动是“每个企业客户重做一遍数据接入”。平台把它做成公共服务：

### 3.1 知识库即服务（KBaaS）

- 统一的文档解析、切块、向量化、检索管道；插件只声明 `knowledgebase.read` 并按
  org 隔离访问
- 插件可选自建私有知识集合（`plugin:<id>:kb` 前缀），复用同一管道
- **RAG 质量公共组件**：标准评测集 + 检索质量报告，帮个体证明“检索效果”——
  企业采购最常问而个体最难回答的问题

### 3.2 工具与连接器市场（MCP 生态复用）

- 平台统一管理的企业系统连接器（ERP/CRM/工单/数据库/Web）以 MCP 服务形式提供，
  第三方 Agent 直接声明调用——mcp 插件的权限组 + 调用网关天然适用
- 连接器本身也可以是第三方贡献的插件 → 市场的第二个供给侧（工具市场）

### 3.3 Agent 运行时组件

- 会话与长期记忆存储（org 隔离、可审计）
- 定时任务与事件驱动触发（复用 platformBus：`iam.user.created → 插件触发流程`）
- 编排能力：复用 app 插件的编排拓扑，向第三方开放子图挂载

## 四、计量计费与分成结算（服务 ⑤⑥，商业层核心）

### 4.1 计量层：一切计费的基础是 usage 事件

audit 的成本归集升级为平台级计量管道：

```
调用发生（模型网关/插件API/工具调用）
  → 网关层统一打 usage 事件（插件自报数据不可信，只作对账参考）:
     usage.recorded {
       subject:    <用户/Agent 身份>        # on-behalf-of 链
       principal:  <plugin:<id> 机器身份>
       org:        <组织>
       resource:   model:xxx | plugin:xxx
       quantity:   { input_tokens, output_tokens, calls }
       unit_cost:  <平台成本价快照>          # 记账时点快照，避免调价纠纷
       list_price: <插件售价快照>
     }
  → audit 持久化（只追加）→ 计费引擎消费
```

三个要点：**计量点在网关不在插件**；**成本价与售价打事件时点快照**；
**归因链复用 on-behalf-of**（A 插件调 B 插件再调模型，成本按链路分摊）。

**schema 一次性定版（本版新增）**：`usage.recorded` 的完整字段
（subject/principal/org/resource/quantity/unit_cost/list_price）在落地顺序
第 2 步随计量管道一次性冻结；计费引擎、分账账本、监控面板、运营洞察此后
**只消费不改版**。后续确需变更走公共事件 deprecation 机制
（`platform.schema.deprecated`），避免第 8 步做账本时返工重算历史数据。
对账三源（账本 = usage 汇总 = 审计抽样）所依赖的告警规则，同样在第 2 步
随 audit 升级一并落地规则框架，之后各步只加规则不改口径。

### 4.2 三层价格结构

| 层 | 内容 | 收取方 | 模式 |
|---|---|---|---|
| L1 模型成本 | tokens 按平台成本价 + 加价率 | 平台（转付模型厂商） | 按量 |
| L2 平台服务费 | 认证/审计/知识库/网关能力使用 | 平台 | 按量/订阅 |
| L3 插件定价 | 开发者自定，平台抽佣 | 开发者 | 订阅/按量/买断 |

`billing.yaml` 声明 L3：

```yaml
billing:
  model: hybrid
  subscription:
    monthly: 999
  usage:
    - key: contract.pages
      unit: 页
      price: 0.5
  commission: platform_default   # 特殊费率存合同不存代码
```

### 4.3 分账账本（ledger）

轻量 `dsh-plugin-billing` 插件，**只追加账本**：

```
每笔 usage 结转生成两条分录：
  debit  org:<orgId>           应付      12.50
  credit developer:<devId>     L3 应收   10.00
  credit platform              L1+L2+佣金 2.50
```

- 账期：企业月度对账（usage 汇总 → 账单 → 确认）；开发者月/季结算（满门槛起付）
- 对账三源：账本 = usage 汇总 = 审计抽样，不一致即告警（复用 audit 告警规则）
- 冲正用红字分录，全程审计留痕
- 防作弊：绕过网关直连模型 → 用量/成本比例异常告警 → 按合同处理

### 4.4 计费演进三阶段

1. **L1 转售先行**：开发者优惠价用平台网关，预充值 + 用量审计，无分成结算（复杂度最低，先聚人）
2. **L3 订阅上架**：市场代收，月度半自动结算
3. **全自动分账**：按量计费 + 自动账本 + 开发者门户自助看量/收入/结算单

## 五、可观测性与托管运维（服务 ⑨）

个体开发者最大的隐性痛点：**一个人扛不住 7×24 运维**。平台把 mcp 插件已有的
运维能力（灰度/回滚/健康熔断/监控）推广为第三方插件的托管服务：

- **托管运行**：插件跑在平台基础设施上，零服务器；平台负责部署、升级、扩缩容
- **插件级监控面板**（开发者门户内）：调用量/延迟/错误率/token 消耗/客户活跃——
  数据全部来自 usage 事件与网关指标，插件无需埋点
- **灰度发布**：新版本先对 1–2 家企业客户灰度（复用 mcp 的灰度机制），出问题自动回滚
- **熔断与限流**：插件故障不拖垮平台（复用健康熔断）；配额防单插件刷爆共享资源
- **故障告警路由**：插件级告警推给开发者本人，平台级告警给平台值班——责任边界清晰
- **SLO 报告**：平台向企业客户出示各插件的可用性/延迟数据——企业敢用的信任基础

## 六、安全合规与治理（服务 ⑩）

企业客户采购第三方应用的最大障碍是信任。平台把合规做成“继承即得”：

- **内容安全**：模型网关统一出口加内容审核/敏感信息过滤（可按企业策略配置），
  插件天然继承，个体无需逐客户对接审核
- **数据分级**：插件在 permissions.yaml 声明数据敏感级别（如 `data: pii-read`），
  安装时企业管理员按数据分级策略放行/拒绝——把“能不能碰敏感数据”从口头承诺变成机制
- **审计继承**：插件所有操作经网关自动进四类审计日志；企业审计员获得对第三方插件的
  只读监督能力（复用 audit 角色）
- **合规文档包**：平台统一提供安全白皮书、数据处理协议（DPA）、渗透测试报告——
  个体拿去应仟企业采购的安全问卷，平台背书
- **上架安全门**：静态扫描 + L1 沙箱 + 出网白名单（见第一节）+ 定期复扫
- **私有化选项**（远期）：企业要求数据不出域时，插件随平台私有化部署——
  得益于“一份插件代码，两种宿主”的既有设计，这是 SaaS 竞品难以复制的优势

---

## 七、插件市场与渠道分发（服务 ⑦）+ 开发者门户（服务 ⑧）

- **市场**：插件详情页（能力声明、权限申请清单透明展示、监控 SLO、客户评价）；
  权限清单透明化本身就是信任机制——企业看得见他申请了什么
- **一键安装**：企业管理员安装时看到权限收缩界面（逐项放行），安装即 RBAC 生效
- **联合销售**：平台销售带着优质插件进企业客户的场景；插件收入分成本就是激励
- **开发者门户**：文档、SDK、devkit、用量/收入/结算面板、工单支持、认证体系
  （开发者认证 → 企业采购信任度加分）
- **头部孵化（路径 C）**：联合品牌、交付实施资源、投资/收购——把头部个体变为 ISV

## 八、关键架构决策与依赖关系

1. **多租户该启动了**：roadmap「多租户三层隔离」的触发条件（单组织树 → 多租户 SaaS）
   已被“开放第三方插件市场 + 对外 IdP”命中。建议**先落多租户，再开市场**，
   否则第一个外部插件上线就要在单租户假设上打补丁。实施要点 roadmap 已记录：
   网关注入 X-Tenant-Id + 剥离伪造头 + 存储强制 scope + 角色只挂 organization_members。
2. **依赖链**：市场（⑦）依赖 沙箱契约（①）+ 多租户 + 计量（⑥依赖 audit 升级）；
   IdP 对外（②模式B）依赖 RS256/JWKS 暂缓项启动；
   **L1 沙箱是独立自研里程碑**（自定义模块加载器），排在 L0 市场验证之后立项，
   不阻塞第 7 步。
3. **计量先行于结算**：usage 事件管道是计费、监控（⑨）、运营洞察的共同地基，
   最早做、最优先做；**其 schema 在第 2 步定版后只增不改版**（见 4.1）。

## 九、落地顺序

```
第 1 步  token scope/audience 改造（模式 A 前置，小改动）
第 2 步  usage 计量管道统一（audit 升级）
         + usage.recorded schema 一次性定版（含 unit_cost/list_price 快照字段）
         + 对账告警规则框架就位——监控/计费/运营共同地基
第 3 步  第三方插件契约 + 沙箱（存储命名空间 + capabilities + 事件命名空间）
         + dshctl plugin init 脚手架
         验证方式（硬性验收标准）：app 插件按第三方契约重写跑通，未通过则契约不冻结
第 4 步  多租户三层隔离（roadmap 暂缓项启动，市场前置）
第 5 步  L1 模型转售（预充值 + 用量审计）+ 开发者门户 v1（用量面板）
第 6 步  OIDC Provider（RS256/JWKS，模式 B）——不做插件化的个体也能被绑定
第 7 步  L0 声明式插件上架 + 插件市场 beta + L3 订阅代收
第 8 步  托管运维推广（灰度/熔断/监控面板面向第三方）+ 分账账本
第 9 步  知识库即服务 / 连接器市场 / 安全合规包（按市场需求排期）
第 10 步 L1 托管 JS 沙箱立项（独立自研里程碑：自定义模块加载器 + ctx 代理
         + 能力裁剪 + 资源配额；依 L0 市场验证的付费信号决定优先级）
```

每步均可独立产生价值；1–3 步不依赖多租户，可立即启动；
第 7 步（市场 beta）不依赖 L1 沙箱——L0 声明式插件先行承接供给。
